# SRA-401 — Quiz schema and safe migration

**Phase:** 4 — Daily MCQ quiz (web) · **Status:** not started

## Summary

Add the four tables the quiz feature needs — `quiz_sets`, `quiz_questions`,
`quiz_attempts`, `quiz_answers` — to the existing SQLModel metadata, and ship an
Alembic migration that preserves every Phase 1–3 row in place. After this ticket
the database can store one quiz set per `(entry_id, generated_on)` per user, hold
each question's text and option list together, record an attempt with its mode and
snapshot counts, and keep one `QuizAnswer` per question per attempt. This is
**schema only**: no quiz is generated, no route exists, and no user can start an
attempt. The agent, the job, the routes, and the UI are SRA-402 through SRA-405.

## Unlocks

- SRA-402 can persist a generated `QuizSet` and its `QuizQuestion` rows.
- SRA-403 gets its nightly idempotency guard from `uq_quiz_sets_entry_generated_on`.
- SRA-404's routes can resolve quizzes only for the authenticated user.

Constraint names: `uq_quiz_sets_entry_generated_on` on `quiz_sets (entry_id, generated_on)`
and `uq_quiz_answers_attempt_question` on `quiz_answers (attempt_id, question_id)`.

> **Note:** `quiz_sets.user_id` is deliberately denormalized so `GET /api/v1/quiz/today`
> filters `WHERE user_id = :uid AND generated_on = today` without joining
> `study_entries`. `question_count` and `option_count` are a snapshot of the user's
> preference at generation time, so changing the preference later does not reshape a
> saved quiz.

> **Note:** The user-preference columns `quiz_question_count` and `quiz_option_count`
> are **not** in this ticket — they land in SRA-501.

## Acceptance criteria

- [ ] `quiz_sets`, `quiz_questions`, `quiz_attempts`, and `quiz_answers` exist with the columns, indexes, and unique constraints from technical design §2.2
- [ ] A fresh `alembic upgrade head` succeeds and creates the four tables with their foreign keys pointing at the existing tables
- [ ] A Phase 3 database with one user, one entry, and six pending reviews upgrades without losing IDs, foreign keys, or schedules; the same pre-existing rows survive a downgrade and a subsequent upgrade
- [ ] Inserting a second `QuizSet` with the same `(entry_id, generated_on)` violates the unique constraint; inserting a second `QuizAnswer` for the same `(attempt_id, question_id)` violates the unique constraint
- [ ] `QuizAttempt.started_at` and `QuizAnswer.answered_at` defaults are timezone-aware, matching the project's `_utcnow()` convention
- [ ] `QuizSet.question_count` and `QuizSet.option_count` snapshot the user's preference at generation time; `options` JSON round-trips a list of strings
- [ ] No production credentials, no live OpenAI calls, and no Phase 3 regression tests are broken by this ticket

## Tests

```bash
source .venv/bin/activate
pytest tests/unit/test_quiz_models.py -v
pytest tests/integration/test_phase4_migration.py -v
pytest -m 'not phase4' -q
ruff check .
pyright
```

`tests/conftest.py` builds an isolated in-memory SQLite engine per test, so the new
tables are observable immediately for unit tests — but `create_all` is not evidence
that an existing database upgrades, hence the separate file-database rehearsal.

## Manual verification

- [ ] Back up a disposable copy of a Phase 3 database, point `DATABASE_URL` at it, record `users` / `study_entries` / `review_schedules` IDs and counts before
- [ ] `alembic upgrade head`; record the same IDs and counts after and confirm they are unchanged
- [ ] Inspect the four new tables for their columns, indexes, and both unique constraints
- [ ] Insert a duplicate `(entry_id, generated_on)` `QuizSet` by hand and confirm the constraint fires
- [ ] `alembic downgrade -1`; confirm only the four new tables disappear and the pre-existing rows are still readable
- [ ] `alembic upgrade head` again; confirm the four tables return
- [ ] Do not use a production or only copy of study data for the first migration run
